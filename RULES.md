# TsqlFormatter — справочник реализованных правил

Полный перечень того, что форматтер делает **сейчас**, по категориям, с примерами
«вход → результат». Отражает фактическое поведение кода (Lexer → Parser →
FormatterEngine + Rules), а не план. Бейдж-`id` каждого правила совпадает со значением
поля `Rule` в тестах — по нему запускается `run-tests.bat --rule <id>`.

- Правил: ~86 · Тестов: 315/315 · Движок: .NET 5
- Источник истины — код: `Core/Lexer.cs`, `Core/Parser.cs`, `Formatting/FormatterEngine.cs`, `Rules/*.cs`
- Индентация везде — символы табуляции (`\t`)

## A. Регистр и литералы

### `1.1` — Ключевые слова в нижний регистр, идентификаторы сохраняют регистр
Служебные слова (`select`, `from`, `where`, `inner join`…) → нижний регистр. Имена таблиц/колонок остаются как есть.

```sql
-- вход
SELECT Id, NAME from dbo.Users WHERE Status = 1
-- результат
select
	Id,
	NAME
from dbo.Users
where
	Status = 1
```

Список служебных слов — в `Lexer.SqlKeywords`. Слово, которого там нет, форматтер считает
идентификатором и регистр ему не меняет: именно так `ASSEMBLY` и `REFERENCES` оставались
в верхнем регистре, пока не были добавлены в список. Обратное тоже верно: слово из списка
по-прежнему годится в качестве имени или псевдонима (`select assembly from dbo.assembly as t`) —
служебными считаются только те позиции, где по грамматике стоит ключевое слово.

```sql
-- вход
drop ASSEMBLY bgbilling_synchronization;
constraint FK_Products foreign key (accountId) REFERENCES Accounts(accountId)
-- результат
drop assembly bgbilling_synchronization;
constraint FK_Products foreign key (accountId) references Accounts(accountId)
```

### `nstring` — Строковые литералы сохраняются дословно
Юникод-префикс `N'…'`, экранированные кавычки `''`, содержимое строк не изменяются.

```sql
-- вход
select @city=N'***', @x=N'it''s ok'
-- результат
select @city = N'***',
	@x = N'it''s ok'
```

### `atat` — Глобальные переменные `@@…` — один токен
`@@TRANCOUNT`, `@@ROWCOUNT`, `@@IDENTITY` лексятся целиком, а не как `@` плюс `@TRANCOUNT`
(раньше из-за этого `if @@TRANCOUNT > 0` разваливалось на `if @` и отдельную строку с `@TRANCOUNT`).
Регистр сохраняется, как у обычных переменных.

```sql
-- вход
if @@TRANCOUNT > 0
commit transaction
-- результат
if @@TRANCOUNT > 0
commit transaction
```

### `dquote` — Идентификаторы в `[…]` и `"…"` дословно
Квадратные и двойные кавычки сохраняются, включая экранирование `""`.

```sql
-- вход
select "core_contract"."id" from "core_contract"
-- результат
select
	"core_contract"."id"
from "core_contract"
```

### `number` — Числа сохраняются (экспонента, знак)
`1e-5`, отрицательные литералы `-1` не ломаются при лексинге.

```sql
-- вход
select 1e-5 as x
-- результат
select
	1e-5 as x
```

### `hex` — Шестнадцатеричные литералы `0x…` — один токен
`0x1F` не распадается на число и «идентификатор» (раньше `select 0x1F as mask`
превращалось в мусор `0 as x1F, as as mask`).

```sql
-- вход
select 0x1F as mask from t where flags & 0x0F = 0x01
-- результат
select
	0x1F as mask
from t
where
	flags & 0x0F = 0x01
```

### `alias` — Неслужебное ключевое слово как алиас без `as`
Слова вроде `day`, `year`, `key` лексер знает как ключевые, но в T-SQL они не
зарезервированы и могут быть «голым» алиасом: `select getdate() day` →
`getdate() as day` (а не две колонки).

## B. Уровень скрипта: границы, пустые строки, GO

### `blanklines` — Пустые строки между операторами сохраняются из оригинала
Пустая строка между двумя операторами ставится **только если она была** в исходнике. Лишние не добавляются, существующие не удаляются.

```sql
-- вход (без пустой строки)
select 1 from t
select 2 from t
-- результат
select
	1
from t
select
	2
from t
```

### `go` — GO не схлопывается и всегда окружён пустыми строками
Каждый `GO` сохраняется отдельно (подряд идущие не объединяются), вокруг каждого — пустая строка. Ведущий `GO` без операторов до него отбрасывается. Счётчик повторов `GO 5` сохраняется вместе с `GO`.

```sql
-- вход
select 1
GO
GO
select 2 from t
-- результат
select
	1

GO

GO

select
	2
from t
```

### `stmtbound` — SELECT без FROM завершается на новом операторе
Присваивающий `select @x = 1` без FROM корректно завершается перед следующим оператором (`declare`, `exec`, `insert`, `if`, `while`, `set`, `commit` и др.), а не поглощает его как «колонки».

```sql
-- вход
select @yy=2026,@mm=6
declare @z int
-- результат
select @yy = 2026,
	@mm = 6
declare @z int
```

То же верно и для операторов, которые выводятся «как есть» (`exec`, `print`): они заканчиваются
перед ключевым словом, с которого может начинаться только новый оператор — `set`, `print`,
`exec`, `raiserror`, `throw`, `truncate`, `waitfor`, `goto`, `break`, `continue`. Раньше
`exec … @m = @mm` проглатывал следующий `set` и обе строки склеивались в одну.

```sql
-- вход
exec webcar.dbo.[p] @y = @yy, @m = @mm set @mm = @mm + 1
-- результат
exec webcar.dbo.[p] @y = @yy, @m = @mm
set @mm = @mm + 1
```

Дополнительно: колонки продолжаются **только после запятой**, а условия `where`/`on` —
только после `and`/`or`. Поэтому нераспознанный оператор на следующей строке
(`use mydb`, `open cur` и т.п.) не втягивается в список с «дорисованной» запятой:

```sql
-- вход
select 1 as x
use mydb
-- результат
select
	1 as x
use mydb
```

### `tran` — BEGIN TRAN / COMMIT / ROLLBACK — операторы, а не блок
`begin tran[saction] [имя]` не принимается за начало блока `begin … end` (раньше
форматтер «дорисовывал» несуществующий `end` и утаскивал `commit` внутрь условий).
`commit` / `rollback` [`tran`|`work`] [имя] — самостоятельные операторы; ключевые
слова в нижний регистр, имя транзакции сохраняет регистр. Слово `transaction`/`tran`/`work`
подхватывается, даже если в исходнике стояло на следующей строке: `commit` и `transaction`
собираются в одну строку (имя транзакции по-прежнему берётся только с той же строки, чтобы не
утащить следующий оператор).

```sql
-- вход
if @@TRANCOUNT > 0
rollback
transaction
-- результат
if @@TRANCOUNT > 0
rollback transaction
```

```sql
-- вход
BEGIN TRAN
update t set x = 1 where id = 5
COMMIT
-- результат
begin tran
update t
set
	x = 1
where
	id = 5
commit
```

Незакрытый `begin` без парного `end` не форматируется — исходник возвращается без
изменений (см. `parse-safety`), вместо добавления фиктивного `end`.

### `lineend` — Перевод строки в конце не добавляется
Конец результата повторяет конец исходника: выделение, не заканчивавшееся переводом строки, не
получает его при форматировании (иначе после вставки обратно в SSMS появлялась бы лишняя пустая
строка). Если перевод строки был — он и остаётся, ровно один.

### `meta` — Идемпотентность + `;` перед WITH
Повторное форматирование даёт тот же результат (проверяется автоматически). Ведущая `;` перед первым оператором (`;with …`) сохраняется. `;` перед **не первым** `with` (CTE после другого оператора) тоже сохраняется — в T-SQL она обязательна:

```sql
-- вход
select 1 as a
;with cte as (select 2 as b) select * from cte
-- результат
select
	1 as a
;with cte as (
	select
		2 as b
)
select
	*
from cte
```

### `semi` — Точка с запятой остаётся там, где её написали
`;` в конце оператора сохраняется и печатается **вплотную** к последнему токену — до хвостового
комментария, чтобы не оказаться закомментированной. `;` также **завершает оператор**: цепочка
`print 'a'; print 'b';`, написанная в одну строку, раскладывается по строкам. `;`, написанная на
отдельной строке, свою строку сохраняет. Раньше точки с запятой терялись, печатались через
пробел (`print 'a' ;`) и не разделяли операторы.

```sql
-- вход
PRINT 'a'; PRINT 'b';
SELECT [c] FROM dbo.Weird;  -- заметка
SELECT 5 --2
;
-- результат
print 'a';
print 'b';
select
	[c]
from dbo.Weird;		-- заметка
select
	5		--2
;
```

Имена сессионных опций `set` (`QUOTED_IDENTIFIER`, `ANSI_NULLS`, `XACT_ABORT`, …) — ключевые
слова, поэтому приводятся к нижнему регистру: `SET QUOTED_IDENTIFIER ON;` → `set quoted_identifier on;`.
Так же трактуются `CONTINUE`, `BREAK`, `GOTO`, `WAITFOR`.

`;` сохраняется и **внутри блоков** `begin … end`, в том числе у `set`, `return`,
`begin/commit/rollback transaction` — раньше эти операторы её проглатывали.

```sql
-- вход
while @i < 10
begin
SET @i += 1; -- шаг
IF @i = 5 CONTINUE;
end;
-- результат
while @i < 10
begin

	set @i += 1;		-- шаг

	if @i = 5
	continue;

end;
```

### `function` — CREATE/ALTER FUNCTION/PROCEDURE и процедурное тело
Программируемые объекты форматируются:
- открывающая `(` списка параметров — **на строке с именем**; каждый параметр на своей строке с табом (хвостовые комментарии сохраняются);
- `returns …` и `as` — на отдельных строках; тело `begin … end` по правилу 2.8;
- `if` и `while`: первое условие — на строке ключевого слова, остальные с табом, тело — на
  следующей строке на том же уровне (см. `if`);
- `set @x op expr`, `return [expr]` — по строке; ключевые слова и системные функции (`exp`, `isnull`, …) в нижнем регистре; имена с схемой (`dbo.fn`) регистр сохраняют;
- составной оператор `+=` / `-=` / `*=` / `/=` не разбивается на части.

```sql
-- вход
create function dbo.f(@a int) returns int as begin if @a is null return 0; return @a; end go
-- результат
create function dbo.f (
	@a int
)
returns int
as
begin

	if @a is null
	return 0

	return @a

end

GO
```

Парсер защищён от зацикливания: любой цикл разбора гарантированно продвигается вперёд, а при
неразрешимой ошибке разбора исходник возвращается без изменений (см. `parse-safety`).

### `cmt-safety` — Комментарий в любом месте не ломает форматирование
T-SQL разрешает комментарий между **любыми** двумя токенами, и научить парсер каждому такому
месту по отдельности нельзя. Поэтому действует общая защита:

1. Комментарий, попавший туда, где ожидался операнд (`where x = --note`), или внутрь составного
   имени (`dbo.--note`), не считается ни значением, ни частью имени: он «паркуется» и выводится
   **на своей строке над оператором**. Раньше в первом случае разбор падал и не форматировался
   весь скрипт, во втором — комментарий вклеивался в имя таблицы (`from dbo.--note as Users`),
   то есть ломался сам SQL.
2. Результат форматирования **сверяется с исходником**: ни один токен и ни один комментарий не
   должен пропасть, и после `--` комментария не должно оказаться кода (иначе он был бы
   закомментирован). Если раскладка это нарушает, форматтер пробует ещё раз, вынося все
   комментарии над операторами; если и так не выходит — возвращает исходник без изменений.
3. Текст, **похожий** на комментарий, комментарием не считается: `--` и `/*` внутри строки
   (`print 'это -- не комментарий'`), внутри `[имени]` или `"имени"`. Экранированная `]]` внутри
   скобочного имени читается как одна `]` — раньше `[col]]--umn]` разваливалось на три токена и
   остаток строки уходил в комментарий.
4. Блочный комментарий, написанный **вместо пробела** внутри выражения (`10 /* note */ / 2`), не
   обрывает выражение: он остаётся на месте, а операнды и оператор — на одной строке. Раньше
   хвост выражения (`/ 2`) уезжал на отдельную строку как неразобранный текст.

Проверяется автоматически: тесты подставляют комментарий (`--` и `/* */`) в каждую позицию между
токенами каждого тестового скрипта — несколько тысяч вариантов — и требуют, чтобы ни в одном
не потерялся текст, не потерялся комментарий и ничто не спряталось за `--`. Счётчик
«left unformatted» в отчёте показывает, сколько таких позиций форматтер пока не раскладывает
(они безопасно возвращаются как есть).

```sql
-- вход
select Id from dbo.--note
Users where Status = 1
-- результат
--note
select
	Id
from dbo.Users
where
	Status = 1
```

Отдельная разновидность той же проблемы — комментарий **перед ключевым словом клаузы**
(`from`, `where`, `set`). Проверка «а дальше идёт `from`?» смотрит сквозь комментарии, поэтому
комментарий больше не прячет за собой клаузу. Комментарий, написанный на строке самого
оператора, там и остаётся; написанный на отдельной строке — сохраняет свою строку.

```sql
-- вход
delete d  /* !!!!!!!! */
from webcar.dbo.t d
where d.mm = @mm
 and d.yy = @yy
-- результат
delete d/* !!!!!!!! */
from webcar.dbo.t as d
where
	d.mm = @mm
	and d.yy = @yy
```

```sql
-- вход
update t
--set b = 2
set a = 1
--note
where x = 1
-- результат
update t
--set b = 2
set
	a = 1
--note
where
	x = 1
```

### `cmt-inline` — Строчный комментарий, мешающий раскладке, становится блочным
Если по правилам за комментарием на той же строке должен идти код (имя таблицы после
`left join`/`from`, список колонок после имени в `create table`), то `--` комментарий там жить не
может — всё, что за ним, оказалось бы закомментировано. Такой комментарий выводится в виде
`/*текст*/` и остаётся на месте, а код встаёт за ним. Текст комментария не меняется (если внутри
уже есть `*/`, комментарий остаётся строчным, чтобы не сломать смысл).

```sql
-- вход
LEFT JOIN -- тип соединения
     dbo.Orders AS o
-- результат
	left join /*тип соединения*/ dbo.Orders as o
```

```sql
-- вход
CREATE TABLE dbo.T  -- комментарий после имени
(
id int not null
)
-- результат
create table dbo.T /*комментарий после имени*/ (
	id int not null
)
```

Блочный комментарий в такой позиции ведёт себя так же — таблица подтягивается к нему на строку.
Раньше комментарий на месте имени превращал само имя в алиас: `from /*note*/ as dbo` и `.Orders`
отдельной строкой.

```sql
-- вход
SELECT status, total
FROM /*таблица должна быть рядом с from*/
dbo.Orders
-- результат
select
	status,
	total
from /*таблица должна быть рядом с from*/ dbo.Orders
```

Блочный комментарий, написанный **вплотную к операнду**, остаётся при нём — это обычный приём
«закомментированный кусок кода вокруг значения». Раньше такие комментарии выносились в начало
скрипта.

```sql
-- вход
where BIG_DATA.DATE BETWEEN /*dateadd(month,-2,*/@from/*)*/ and @to
-- результат
where
	BIG_DATA.DATE between /*dateadd(month,-2,*/@from/*)*/ and @to
```

Обратное правило: если на строке с блочным комментарием **больше ничего нет** и после него был
перенос строки, комментарий остаётся на своей строке, и код снизу к нему не подтягивается
(правило `blockcmt`).

```sql
-- вход
ROW_NUMBER() OVER (
     /* без PARTITION BY */
     ORDER BY a.total_amount DESC -- по убыванию суммы
) AS rn
-- результат
row_number()
	over (
		/* без PARTITION BY */
		order by
			a.total_amount desc		-- по убыванию суммы
	) as rn
```

### `parse-safety` — Graceful degradation: «не смог — не трогаю»
Главный приоритет — **не ломать синтаксис/семантику SQL**. Если конструкцию не удаётся
распарсить надёжно (парсер бросает `ParseException`), форматтер возвращает **исходный текст
без изменений**, а не выдаёт частично-переформатированный (битый) результат.

Исключение — оборванный «хвост»: если выделение обрывается посреди конструкции (например,
`from openquery(` без продолжения), форматируется **самая длинная часть, которая разбирается**
(включая начало самого оборванного оператора), а незавершённый остаток выводится дословно и
остаётся на той строке, где был написан. Раньше из-за такого хвоста не форматировался весь скрипт.

```sql
-- вход
create table #process (
object_type varchar(255),
object_id int
)

insert into #process(
object_type,
object_id
)
select
object_type,
object_id
from openquery(
-- результат
create table #process (
	object_type varchar(255),
	object_id int
)

insert into #process (
	object_type,
	object_id
)
select
	object_type,
	object_id
from openquery(
```

Если не разбирается вообще ничего (например, `begin` без парного `end`), исходник возвращается
без изменений, как и раньше. Разобранная часть дополнительно **сверяется по токенам** с исходником:
если при форматировании префикса что-то из текста пропало бы (скажем, повисшее `where` перед
оборванной скобкой), оборванный оператор целиком остаётся дословным. Также `--`
комментарий никогда не становится «выражением»/операндом, а комментарии не сбивают парсер
(метод `Expect` пропускает их и, при необходимости, переносит к следующему узлу).

## C. Комментарии

> Ключевой принцип: комментарий остаётся привязанным к той строке, рядом с которой был.
>
> Исключение — аварийный режим: комментарий, которому в раскладке места нет, поднимается
> **над оператором**, а если сверка вывода с исходником не сошлась — над операторами
> оказываются сразу **все** комментарии. Это защита от потери текста, а не правило
> раскладки (см. `cmt-safety`).

Правил про комментарии девять, и часть из них живёт в других блоках:

| id | о чём | блок |
|---|---|---|
| `comments` | отдельный комментарий → следующий оператор | C |
| `fromcmt` | хвостовой комментарий у таблицы FROM / JOIN | C |
| `4.1.2` | хвостовой `--` остаётся на своей строке | C |
| `blockcmt` | блочные `/* */` прозрачны | C |
| `linecmt` | `--` в списках: своя строка, запятая перед комментарием | C |
| `stmtcmt` | комментарий строкой ниже не приклеивается к предыдущему оператору | C |
| `cmt-safety` | комментарий в любом месте не ломает форматирование | B |
| `cmt-inline` | `--` становится `/* */`, если за ним должен идти код | B |
| `blanklines` | пустые строки вокруг комментария берутся из исходника | B |

### `comments` — Отдельный комментарий привязывается к следующему оператору
Комментарий на своей строке приклеивается к оператору снизу без пустой строки (если её не было); пустая строка сохраняется, если была.

```sql
-- вход
-- header
select a from t
-- результат
-- header
select
	a
from t
```

Комментарий после `from` остаётся внутри `select` только если оператор **продолжается**, то есть
дальше идёт любая клауза этого же оператора: `where` / `group by` / `having` / `order by` /
`option` / `union` / `except` / `intersect`. Иначе он относится к следующему оператору, и
окружавшие его пустые строки сохраняются.

Комментарий перед клаузой, которая продолжает **сам источник**, обрабатывается на месте и клаузу
не прячет: перед `join` / `cross apply` — строкой выше джойна; перед `pivot`/`unpivot` — строкой
выше блока; перед запятой списка `from` — уходит на строку источника, который был до неё; перед
хинтом `with (nolock)` — поднимается над оператором (на строке хинта места нет). Раньше три
последних случая ломали разбор: `pivot` и вторая таблица выпадали в неразобранный текст, а из-за
комментария перед хинтом не форматировался весь скрипт.

```sql
-- вход
select a
from t

--следующий шаг

select b
from t
-- результат
select
	a
from t

--следующий шаг

select
	b
from t
```

### `4.1.2` — Хвостовой `--` комментарий остаётся на своей строке
Комментарий в конце строки колонки, условия или таблицы FROM остаётся на этой строке, отделённый двумя табами. Запятая — перед комментарием.

```sql
-- вход
select a, --первая
b --вторая
from t
-- результат
select
	a,		--первая
	b		--вторая
from t
```

### `fromcmt` — Хвостовой комментарий у таблицы FROM / JOIN не «уезжает»
Комментарий на строке `from t1` остаётся там, а не мигрирует к следующему оператору — и строчный,
и блочный (раньше блочный уезжал на свою строку: правило работало только для `--`). То же и на
строке `join`: `left join dbo.users as ug  --создал процесс` — комментарий остаётся на строке
джойна и **не прячет следующий за ним `on`** (раньше из-за него джойн оставался без условий, и
дальше разваливался весь скрипт). Комментарий, стоящий отдельной строкой между джойном и `on`,
выводится строкой выше `on`.

```sql
-- вход
select a from t1  -- про t1
select b from t2
-- результат
select
	a
from t1		-- про t1
select
	b
from t2
```

### `blockcmt` — Блочные `/* */` комментарии прозрачны
Блочные комментарии в T-SQL **вкладываются**: `/* a /* b */ c */` — один комментарий,
лексер отслеживает глубину и не обрывает его на первом `*/`.

Блочные комментарии **игнорируются** при разборе структуры: остальные правила применяются так,
будто их нет, и комментарий не разбивает конструкцию.

Разделитель перед блочным комментарием — **один пробел**, в том числе после запятой и после
открывающей скобки. Единственное исключение — комментарий, написанный **вплотную к значению**
(`6/*7,8,9,0*/`, `@from/*)*/`): такой комментарий становится частью самого значения и печатается
ровно так, как написан. Решает именно исходник: `2 /*two*/` сохранит пробел, `2/*two*/` — склейку.
Правило одинаково работает в списке колонок, в условиях, в IN-списке, в `group by`/`order by`,
а также на уровне предложений — `into #wru/*коммент*/` и источник `from … as u/*коммент*/`
сохраняют склейку так же, как значение. Строчный `--` всегда отделяется двумя табами — в том
числе когда он закрывает строку с `)` закрытой группы условий или IN-списка.

Одно уточнение: если за источником `from` идёт запятая (список источников), запятая закрывает
источник и приклеенный комментарий уезжает за неё — `from t1 as a/*one*/, t2` даёт
`from t1 as a, /*one*/`. Комментарий не может остаться приклеенным к тому, что теперь стоит
перед запятой.

```sql
-- вход
select wrg.cityid
into #wru/*коммент into*/
from webcar.dbo.wage_register_users as u/*коммент from*/
left join crm.dbo.user_group as g
on g.user_id = u.crm_userid
and g.group_id in (
1607,		--Уфа 2 категория
1730		--СТП
) -- логические группы
-- результат
select
	wrg.cityid
into #wru/*коммент into*/
from webcar.dbo.wage_register_users as u/*коммент from*/
	left join crm.dbo.user_group as g
		on g.user_id = u.crm_userid
		and g.group_id in (
			1607,		--Уфа 2 категория
			1730		--СТП
		)		-- логические группы
```

```sql
-- вход
select a from t where x in (1, 2 /*spaced*/, 3/*glued*/)
-- результат
select
	a
from t
where
	x in (1, 2 /*spaced*/, 3/*glued*/)
```

Смысл исключения: `/* */` вплотную к значению — это обычно **закомментированный кусок кода**
(`between /*dateadd(month,-2,*/@from/*)*/ and @to`), и добавленный пробел изменил бы то, что
получится после раскомментирования.

```sql
-- вход
update t /* про таблицу */
set a = 1, /* про a */
b = 2 /* про b */
-- результат
update t /* про таблицу */
set
	a = 1, /* про a */
	b = 2 /* про b */
```

Комментарий, написанный **после запятой** и закрывающий свою строку, остаётся на строке того
значения, которое эта запятая закрыла. Если же за комментарием на той же строке идёт следующее
значение, комментарий относится к нему (и переносить его вниз не надо — переноса в исходнике не
было). Раньше в первом случае комментарий съезжал на следующую строку и приклеивался к
следующему значению, забирая его перенос строки.

```sql
-- вход
and g.group_id in (
1607,		--Уфа 2 категория
1608,		/*Уфа 1 категория*/
1609,		--СУПК 3 категория
)
-- результат
and g.group_id in (
	1607,		--Уфа 2 категория
	1608, /*Уфа 1 категория*/
	1609,		--СУПК 3 категория
)
```

Отступ зависит от того, как комментарий написан:

- комментарий, **вклеенный** к предыдущему токену (значению, колонке, запятой), там и остаётся —
  таб перед ним не добавляется;
- комментарий, стоящий **отдельной строкой** (после него в исходнике был перенос), сохраняет свою
  строку и получает **отступ текущего уровня**: в списке колонок — +1 таб, внутри `over (` — +2
  таба. Код со следующей строки к нему не подтягивается.

В списке колонок скрипт раскладывается так, **как будто блочных комментариев нет**: каждая колонка
начинается со своей строки (правило `2.1`). Сам комментарий остаётся там, где его написали:
начался на строке предыдущей колонки — там и останется (вплотную после запятой), стоял отдельной
строкой — останется отдельной строкой. Перенос между `*/` и колонкой берётся из исходника; если
переноса не было вовсе, обязательный перенос списка ставится **после** комментария — кроме случая,
когда комментарий сам **многострочный**: перенос строки уже есть внутри самого комментария,
поэтому обязательный не добавляется, и колонка остаётся на строке с `*/`:

```sql
-- вход
select '...' as [sql_text], /* [Alias] = expr, INNER JOIN */ c.[id] from [dbo].[C] c
-- результат
select
	'...' as [sql_text],/* [Alias] = expr, INNER JOIN */
	c.[id]
from [dbo].[C] as c
```

```sql
-- вход
select
c.title, /*note
note*/ 12 as a
from a as c
-- результат
select
	c.title,/*note
note*/ 12 as a
from a as c
```

```sql
-- вход
select
c.title,
/*note*/
12 as a
from a as c
-- результат
select
	c.title,
	/*note*/
	12 as a
from a as c
```

В IN-списке блочный комментарий остаётся там, где стоял, и список не разбивается на строки:
написанный **после** значения — остаётся при нём (вплотную или через пробел, как в исходнике),
написанный **перед** значением (в том числе перед самым первым) — остаётся перед ним:

```sql
-- вход
select * from a where id in (1, 2, 3, 4, 5, 6/*7,8,9,0*/, 1, 2, 3, 4)
-- результат
select
	*
from a
where
	id in (1, 2, 3, 4, 5, 6/*7,8,9,0*/, 1, 2, 3, 4)
```

```sql
-- вход
select * from a where id in (/*11,*/54,/*56,*/24,26)
-- результат
select
	*
from a
where
	id in (/*11,*/54, /*56,*/24, 26)
```

То же в `group by`/`order by` (комментарий остаётся вклеенным к элементу, а не уезжает на свою строку): `… ac.title/*, p1.title*/`.

### `linecmt` — `--` комментарии в списках: на своей строке, запятая перед комментарием
Строчный `--` комментарий **никогда не становится выражением** — но там, где по раскладке за
комментарием должен идти код (имя таблицы после `join`, список колонок после имени в
`create table`), он выводится как `/*текст*/`, см. `cmt-inline`. Внутри списка колонок и
списка условий (`where`/`on`) отдельно стоящий `--` комментарий (в т.ч. закомментированная
колонка/условие) выводится **на своей строке** над элементом; хвостовой `--` комментарий —
после элемента через два таба, при этом **запятая ставится до комментария**.

Отступ отдельно стоящего комментария зависит от того, к чему он относится:

- к **следующему элементу списка** (список продолжается) — отступ элемента, +1 таб:
  `a,` ⏎ `\t-- ,old_col` ⏎ `\tb`;
- к **следующей клаузе** (список закончился) — отступ клаузы, без таба:
  `d.group_id` ⏎ `--  into #tmp` ⏎ `from t as d`.

```sql
-- вход
select --top (@top)
	w.cid as objectId,
	--	'' as comment,
	ac.title as city_title,
	b.c	--note
from t
-- результат
select		--top (@top)
	w.cid as objectId,
	--	'' as comment,
	ac.title as city_title,
	b.c		--note
from t
```

Комментарий, написанный **на строке самого `select`** и при этом **до первого элемента списка**,
там и остаётся (через два таба) — он относится к оператору, а не к первой колонке, и не переезжает
на её строку. Если перед ним на этой строке уже есть колонка (`select a, --первая`), комментарий
хвостовой для этой колонки и уезжает вместе с ней (правило `4.1.2`). Комментарий, написанный ниже,
на отдельной строке, свою строку сохраняет.

Блочный `/* */` в этом месте ведёт себя так же — остаётся на строке `select`, через **один
пробел** (он занимает место пробела, который там и был). Неважно, был ли после него перенос
строки: колонки всё равно начинаются каждая со своей строки, поэтому то, что стояло за
комментарием, уезжает вниз (правило `blockcmt`).

```sql
-- вход
select /* между SELECT и списком */ 1 as one;
-- результат
select /* между SELECT и списком */
	1 as one;
```

Комментарии, написанные **вокруг `as`**, остаются на строке колонки, по пробелу с каждой
стороны. Раньше они обрывали список колонок, и `as … one` уходило в неразобранный текст.

```sql
-- вход
SELECT 1 /* перед AS */ AS /* после AS */ one;
-- результат
select
	1 /* перед AS */ as /* после AS */ one;
```

```sql
-- вход
select  -- делитель для коэф. услуг по процессу
  d.process_id, count(1) as [n]
 into #enter
 from #DATA as d
 group by d.process_id
-- результат
select		-- делитель для коэф. услуг по процессу
	d.process_id,
	count(1) as [n]
into #enter
from #DATA as d
group by
	d.process_id
```

Комментарий между колонками не обрывает список и при «запятой в начале строки»: в стиле

```
	a
	--note
	,b
```
запятая стоит после комментария **в исходнике**, и он относится к следующей колонке. На выходе
запятая остаётся при предыдущей колонке, а комментарий — на своей строке над следующей (правило
`4.1.2`: запятая всегда **перед** комментарием). Раньше список на этом
заканчивался, а весь остаток оператора (колонки, `join`-ы, `group by`) сваливался в одну строку
без отступов. Комментарий, стоящий перед закрывающей скобкой подзапроса, тоже остаётся на месте —
последней строкой внутри скобок, а не уезжает наверх.

```sql
-- вход
select a
-- ,old_col
,b
from t
where x = 1
-- результат
select
	a,
	-- ,old_col
	b
from t
where
	x = 1
```

То же в списках `group by` и `order by`: отдельно стоящий `--` комментарий (например,
закомментированный элемент) остаётся на своей строке над элементом, а не обрывает разбор:

```sql
-- вход
select a, b from t group by a,
--note
b
-- результат
select
	a,
	b
from t
group by
	a,
	--note
	b
```

Комментарий между списком колонок и `into`/`from` (обычно это закомментированная клауза,
`--  into #tmp`) остаётся на своём месте — отдельной строкой перед `into`/`from` — и не прячет их
от разбора (раньше из-за него `from` не находился и не форматировался весь скрипт).

```sql
-- вход
select d.group_id
--  into #group_by_org
from t as d
where d.id = 1
-- результат
select
	d.group_id
--  into #group_by_org
from t as d
where
	d.id = 1
```

Комментарий на той же строке, что и открывающая `(` подзапроса (`exists ( --note`), остаётся на этой строке; комментарий на отдельной строке — над `select` внутри скобок.

### `stmtcmt` — комментарий на следующей строке не приклеивается к предыдущему оператору
`declare`, `drop table` и т.п. больше не «воруют» комментарий со строки ниже — он остаётся
самостоятельным и относится к следующему оператору. Хвостовой `--` комментарий на строке
`drop table … #t` не вклеивается в имя таблицы.

## D. SELECT и список колонок

> Принцип: **каждая** колонка `select` (а также каждый элемент `group by` и `order by`)
> всегда переносится на свою строку с табуляцией — независимо от количества, даже если
> колонка одна.
>
> Единственное исключение: колонка, стоящая сразу за **многострочным** блочным комментарием,
> остаётся на строке с `*/` — перенос уже есть внутри комментария (см. `blockcmt`).

### `2.1` — Колонки, каждая на своей строке (+1 таб)

```sql
-- вход
select a, b, c from t
-- результат
select
	a,
	b,
	c
from t
```

### `2.1.1` — Одна колонка тоже на своей строке

```sql
-- вход
select a from t
-- результат
select
	a
from t
```

### `assign` — Присваивающий SELECT: первое присваивание на строке `select`
Если `select` только присваивает значения переменным (все элементы списка — `@var = выражение`),
он оформляется как `declare`: первый аргумент остаётся на строке `select`, остальные переносятся
с одним табом. Обычный `select`, возвращающий выборку (в т.ч. `select @a, @b`), форматируется по
правилу `2.1` — каждая колонка на своей строке.

```sql
-- вход
select @a = 'делай так', @i = 67, @b = 12.3
-- результат
select @a = 'делай так',
	@i = 67,
	@b = 12.3
```

```sql
-- вход
select @a = t.name, @b = t.cnt from dbo.t as t where t.id = 1
-- результат
select @a = t.name,
	@b = t.cnt
from dbo.t as t
where
	t.id = 1
```

Если над первым присваиванием стоит отдельный `--` комментарий, применяется обычная раскладка
(комментарий не может стоять в одной строке перед выражением).

### `into` — `SELECT … INTO #tbl` отдельной строкой между колонками и `from`

```sql
-- вход
select a, b into #tmp from t where x = 1
-- результат
select
	a,
	b
into #tmp
from t
where
	x = 1
```

### `5.1` — Алиас через `=` переписывается в `expr as alias`

```sql
-- вход
select [Name] = t.col1, cnt = count(*) from t
-- результат
select
	t.col1 as [Name],
	count(*) as cnt
from t
```

### `top` — TOP / DISTINCT / PERCENT / WITH TIES
`top 5 percent`, `top (10) with ties`, `distinct top 10` сохраняются в нормализованном виде.

```sql
-- вход
select top (10) with ties a from t order by a
-- результат
select top (10) with ties
	a
from t
order by
	a
```

Комментарий между `select` и `top`/`distinct` не сбивает разбор: детектор клаузы смотрит **сквозь комментарии**. Раньше `select /*top 10*/ top (@top)` ломал разбор целиком (`top (@top)` принимался за колонку, и весь остаток скрипта вываливался сырым текстом). Теперь `top`/`distinct` распознаётся, а комментарий сохраняется (выносится на свою строку над `select`):

```sql
-- вход
select /*top 10*/ top (@top) a as x, b as y from t
-- результат
/*top 10*/
select top (@top)
	a as x,
	b as y
from t
```

### `2.2` — JOIN на +1 таб, ON на +2 таба; нормализация типа JOIN
Первое условие — на строке `on`, остальные с новых строк. `left outer join` → `left join`, голый `join` → `inner join`. Алиас `t a` → `t as a`.

```sql
-- вход
select t.a, u.b from t
inner join u on u.id=t.id and u.x=t.y
-- результат
select
	t.a,
	u.b
from t
	inner join u
		on u.id = t.id
		and u.x = t.y
```

### `fromlist` — Несколько источников через запятую
Первый источник остаётся на строке `from`, каждый следующий — с новой строки с одной
табуляцией. Запятая закрывает предыдущий источник: она ставится **после** его джойнов и
**перед** его `--` комментарием, чтобы не оказаться закомментированной.

```sql
-- вход
select *
from webcar.dbo.city as t1, 
webcar.dbo.city as t2, 	#test as t3
-- результат
select
	*
from webcar.dbo.city as t1,
	webcar.dbo.city as t2,
	#test as t3
```

```sql
-- вход
select a from t1 as a inner join u on u.id = a.id, t2 as b
-- результат
select
	a
from t1 as a
	inner join u
		on u.id = a.id,
	t2 as b
```

```sql
-- вход
select a from t with (nolock) where x = 1
-- результат
select
	a
from t with (nolock)
where
	x = 1
```

```sql
-- вход

-- результат

from (
	select
		a
	from t

		b = 1
```

### `7` — OPENQUERY: сервер и удалённый SQL на отдельных строках

```sql
-- вход
select w.* from openquery(srv, 'select id from t') as w
-- результат
select
	w.*
from openquery(
	srv,
```

### `pivot` — PIVOT / UNPIVOT блоком
Ключевое слово `pivot` (или `unpivot`) начинает **свою строку** на уровне источника, за ним
пробел и `(`. Агрегат и строка `for … in (` — на +1 таб, каждое значение списка `in` — на своей
строке на +2 таба. Закрывающая скобка списка на +1 таб, закрывающая скобка блока — на уровне
`pivot`, алиас на её строке. Джойны и `where`/`order by` после блока форматируются как обычно.

```sql
-- вход
select pvt.VendorID, pvt.[250] as Emp1
from (select PurchaseOrderID, EmployeeID, VendorID from Purchasing.PurchaseOrderHeader) as p
pivot (count(PurchaseOrderID) for EmployeeID in ([250], [251])) as pvt
order by pvt.VendorID
-- результат
select
	pvt.VendorID,
	pvt.[250] as Emp1
from (
	select
		PurchaseOrderID,
		EmployeeID,
		VendorID
	from Purchasing.PurchaseOrderHeader
) as p
pivot (
	count(PurchaseOrderID)
	for EmployeeID in (
		[250],
		[251]
	)
) as pvt
order by
	pvt.VendorID
```

Комментарии внутри блока остаются в нём: после агрегата — на его строке, после списка `in (…)` —
на строке закрывающей скобки. Раньше они выносились над всем запросом.

`unpivot` устроен так же — на месте агрегата стоит обычная колонка:

```sql
-- вход
select cid, col, val from t unpivot (val for col in (a, b, c)) as u
-- результат
select
	cid,
	col,
	val
from t
unpivot (
	val
	for col in (
		a,
		b,
		c
	)
) as u
```

Разворачивается аналогично JOIN: `cross apply ( … ) as l` с телом на +1 таб.

## F. WHERE и условия

> Принцип: после `where` **каждое** условие — на своей строке с одной табуляцией,
> даже если условие всего одно (`and`/`or` — в начале строки).

### `2.6` — Каждое условие на своей строке (даже одно)

```sql
-- вход
select * from t where x = 1
-- результат
select
	*
from t
where
	x = 1
```

```sql
-- вход
select * from t where a=1 or b=2
-- результат
select
	*
from t
where
	a = 1
	or b = 2
```

### `where-or` — Скобочные группы условий сохраняются, внешние скобки не добавляются
Группа отсчитывает отступ **от той строки, на которой она начинается**: тело — на таб глубже,
закрывающая `)` — вровень с открывающей. Это одинаково работает и в `where`, и в условиях `when`
внутри `case`, и в `if`/`while`. Раньше группа внутри `case` считала отступ от строки `when`, а не
от своей, и вложенным скобкам не хватало табуляций.

```sql
-- вход
when c.status not in (2, 3)
and p.timeTo is not null
and (n.timeFrom > p.timeTo
or (n.timeFrom is null
and p.timeTo < getdate()))
then -1
-- результат
			when c.status not in (2, 3)
				and p.timeTo is not null
				and (
					n.timeFrom > p.timeTo
					or (
						n.timeFrom is null
						and p.timeTo < getdate()
					)
				)
			then -1
```

```sql
-- вход
... where x=1 and (b=1 or b=2) or y>0
-- результат
where
	x = 1
	and (
		b = 1
		or b = 2
	)
	or y > 0
```

Комментарии внутри группы поддержаны: комментарий на строке открывающей `(` остаётся на ней,
отдельно стоящий — на своей строке над условием, хвостовой — после условия через два таба.
Раньше `--` комментарий сразу после `(` уходил в разбор выражения и ронял форматирование всего
скрипта. Одиночное условие в скобках с комментарием тоже выводится «группой» — иначе комментарий
пришлось бы ставить в одну строку с условием, закомментировав его.

```sql
-- вход
select a from t where e.cid is null
and not (  --почему
w.mm_dz = 1
and w.status = 2
)
-- результат
select
	a
from t
where
	e.cid is null
	and not (		--почему
		w.mm_dz = 1
		and w.status = 2
	)
```

### `isnull` / `2.4` — IS [NOT] NULL, IN, NOT IN, LIKE, BETWEEN
`in (subquery)` разворачивает подзапрос на новую строку с отступом. Отрицание — часть оператора и
сохраняется целиком: `not in`, `not like`, `not between` (потерянный `not` перевернул бы условие).

```sql
-- вход
select a from t where x not between 1 and 5 and z not like 'a%'
-- результат
select
	a
from t
where
	x not between 1 and 5
	and z not like 'a%'
```

```sql
-- вход
select * from t where id in (select id from u where u.x=1)
-- результат
select
	*
from t
where
	id in (
		select
			id
		from u
		where
			u.x = 1
	)
```

### `not-exists` — `NOT EXISTS (…)` / `NOT (группа)` — единый узел
Префиксный `not` перед `exists (…)` или перед скобочной группой парсится как **одно**
условие, а не разбивается на `not` и отдельное условие (`and not exists (…)` остаётся целым;
`group by`/следующее условие принадлежат тому же оператору).

## H. Выражения и функции

### `2.15` / `fnbreak` — Функции: короткие inline; с многострочным аргументом — по строкам
Нет пробела перед `(` у функции. Если аргумент многострочный (CASE, подзапрос) — аргументы переносятся по строкам.
Аргументом может быть целое условие с `and`/`or` — `iif(a = 1 and b > 2, 'x', 'y')`, в том числе со
скобочной группой: `iif((a is null or a > @dto) and datediff(...) >= 1, 1, 0)`. Раньше разбор
аргументов останавливался на первом `and` и не форматировался весь скрипт.

```sql
-- вход
select count(*), substring(name,1,3) from emp
-- результат
select
	count(*),
	substring(name, 1, 3)
from emp
```

Комментарий у аргумента остаётся при нём: блочный — inline на месте, где его написали;
строчный `--` заставляет вызов раскладываться по строкам (иначе за ним спрятался бы остаток
вызова), запятая ставится **до** комментария. Раньше такие комментарии выносились над всем
оператором, а вызов схлопывался в одну строку.

```sql
-- вход
select coalesce(
a,   -- основной
b,   -- запасной
'' -- по умолчанию
) as t, iif(total > 1000 /* порог */, 'a', 'b') as n
from t
-- результат
select
	coalesce(
		a,		-- основной
		b,		-- запасной
		''		-- по умолчанию
	) as t,
	iif(total > 1000 /* порог */, 'a', 'b') as n
from t
```

### `sign` — Знак перед операндом: `+14`, `-5`, `-(a + b)`
Знак пишется вплотную к операнду и сохраняется как есть. Раньше ведущий `+` (например
`dateadd(day, +14, BG.close_dt)`) вообще не разбирался и из-за него не форматировался весь
скрипт; а `-(выражение)` разворачивалось в `0 - выражение` — лишний токен, которого в исходнике
не было, из-за чего проверка на сохранность текста отбрасывала форматирование целиком.

```sql
-- вход
select dateadd(day, +14, t.close_dt) as d, -(a + b) as x
from t
where x between -1 and +2
-- результат
select
	dateadd(day, +14, t.close_dt) as d,
	-(a + b) as x
from t
where
	x between -1 and +2
```

### `convert` — CAST / CONVERT сохраняют скобки типа
`varchar(10)`, `decimal(18, 2)` не теряют скобки (ранее превращалось в `varchar10`).

```sql
-- вход
select convert(varchar(10), id) as c, cast(x as varchar(20)) as d from t
-- результат
select
	convert(varchar(10), id) as c,
	cast(x as varchar(20)) as d
from t
```

### `window` — Оконные функции OVER (…): нижний регистр и умные пробелы
`over (` переносится на следующую строку с табом от самой функции; `partition by` и `order by` —
ещё на таб глубже, каждый их элемент — на своей строке с ещё одним табом; закрывающая `)` — на
уровне `over`, алиас остаётся на её строке. Клауза окна (`rows unbounded preceding` и т.п.)
выводится отдельной строкой на уровне `partition by`, её слова (`rows`, `between`, `unbounded`,
`preceding`, `following`, `current`, `row`, `range`) — в нижнем регистре. Ключевые слова в нижнем
регистре, точки и скобки без лишних пробелов. Комментарий у элемента `order by`/`partition by`
остаётся на его строке; комментарий, стоящий отдельной строкой после `over (`, свою строку
сохраняет.

```sql
-- вход
select row_number() OVER (ORDER BY a.[Id]) as [Rn] from t
-- результат
select
	row_number()
		over (
			order by
				a.[Id]
		) as [Rn]
from t
```

```sql
-- вход
select first_value(w.decision_group)
over (
partition by
w.organization_id,new_column
order by
decision_group,new_column
) as updated_decision_group
from #res as w
-- результат
select
	first_value(w.decision_group)
		over (
			partition by
				w.organization_id,
				new_column
			order by
				decision_group,
				new_column
		) as updated_decision_group
from #res as w
```

### `dottedfn` — Функции с составным именем `schema.fn(args)`

```sql
-- вход
select webcar.dbo.datafirst(@yy, @mm) as d from t
-- результат
select
	webcar.dbo.datafirst(@yy, @mm) as d
from t
```

### `2.5` — CASE / WHEN / THEN / ELSE / END (простой и вложенный)

```sql
-- вход
select case when a=1 then 'one' else 'other' end as l from t
-- результат
select
	case
		when a = 1
		then 'one'
		else 'other'
	end as l
from t
```

Несколько условий в одном `when` соединяются через `and` **или `or`** — оператор в **нижнем регистре** и в начале следующей строки (+1 таб), а не хвостом предыдущей:

```sql
-- вход
case when cp.cid is not null and cp.[end] is null then '2100-01-01' ... end
-- результат
case
	when cp.cid is not null
		and cp.[end] is null
	then '2100-01-01'
	...
end
```

Комментарии внутри `case` остаются на своих местах: на строке самого `case`; между условием и
`then` (там `then` всё равно уходит на следующую строку, поэтому безопасен и `--`); блочный
перед значением после `then`; отдельно стоящий комментарий между ветками — на своей строке
на уровне `when`. Раньше комментарий после `case` вообще ломал разбор (скрипт не
форматировался), а хвостовой комментарий ветки утаскивал за собой комментарий следующей.

```sql
-- вход
select case -- начало CASE
when o.status = 1 /* новый */ then N'Новый'
when o.status = 2 then N'В работе' -- в работе
-- отдельный комментарий между ветками
when o.status = 3 then /* завершён */ N'Завершён'
else N'Неизвестно' -- по умолчанию
end as status_name
from t
-- результат
select
	case		-- начало CASE
		when o.status = 1 /* новый */
		then N'Новый'
		when o.status = 2
		then N'В работе'		-- в работе
		-- отдельный комментарий между ветками
		when o.status = 3
		then /* завершён */ N'Завершён'
		else N'Неизвестно'		-- по умолчанию
	end as status_name
from t
```

### `aggdistinct` / `collate` / `exists` / `paren` — Прочие выражения
`count(distinct x)` / `sum(all y)`; `collate Latin1_General_Bin2`; `exists (subquery)`; вложенные скобки и арифметика `((a+b)*(c-d))` сохраняют семантику.

### `expr` — Побитовые операторы `&` `|` `^` остаются inline
Побитовые операторы имеют тот же приоритет, что и `+` / `-`, и **не разбиваются** на отдельные строки (иначе `where` ошибочно принимал бы `&` за отдельное условие).

```sql
-- вход
where main.gr&power(2,0)=0
-- результат
where
	main.gr & power(2, 0) = 0
```

### `2.13` — Многострочный строковый литерал выводится дословно (verbatim)
Содержимое строк (в т.ч. динамический SQL и `--` комментарии внутри) **не трогается**:
многострочные литералы выводятся как есть, без переиндентации. Это защищает выравнивание
шаблонов динамического SQL, собираемых конкатенацией:

```sql
-- вход
declare @x varchar(max) = '
	line1
' + @p + '
	line2
'
-- результат (строки сохранены дословно)
declare @x varchar(max) = '
	line1
' + @p + '
	line2
'
```

### `option` — `OPTION (…)` как хвостовая клауза, а не условие WHERE
Хинт запроса `option(recompile)` / `option(maxdop 1, recompile)` рендерится отдельной
последней строкой на уровне отступа оператора, а не втягивается в список условий `where`.

## I. DECLARE

### `declare` — Первая переменная на строке `declare`, остальные — с табом
Первый аргумент конструкции остаётся на той же строке, где начинается `declare`; каждая следующая переменная переносится на свою строку с одним табом. Типы: `varchar(50)` без внутренних пробелов, `decimal(18, 2)` — пробел после запятой. Табличная переменная — с пробелом перед списком колонок: `@t table (id int, name varchar(50))`. Хвостовой комментарий переменной сохраняется (`--` через два таба, `/* */` вклеивается).

```sql
-- вход
declare @i int, @a varchar(200), @b float
-- результат
declare @i int,
	@a varchar(200),
	@b float
```

```sql
-- вход
DECLARE @label nvarchar(50) = 'a, b, c' -- @x int, @y int
-- результат
declare @label nvarchar(50) = 'a, b, c'		-- @x int, @y int
```

```sql
-- вход
declare @a int = 1, --note
@b varchar(50)
-- результат
declare @a int = 1,		--note
	@b varchar(50)
```

## J. INSERT / UPDATE / DELETE

### `2.12` — INSERT … VALUES / INSERT … SELECT

Список колонок: открывающая `(` — через пробел после имени таблицы (как в `create table`), **каждая колонка на своей строке** (+1 таб), закрывающая `)` на отдельной строке на уровне `insert`. Работает и когда список колонок — единственное, что есть в выделении (без `values`/`select`). Хвостовой `--` комментарий после `)` остаётся на строке с `)` и не разрывает `insert … select` на два оператора.

```sql
-- вход
insert into dbo.t (a,b,c) values (1,2,3)
-- результат
insert into dbo.t (
	a,
	b,
	c
)
values
	(1, 2, 3)
```

Комментарий строки `values` остаётся при своей строке, запятая — **до** комментария:

```sql
-- вход
insert into @tbl (id, val)
values
(1, N'один'),   -- первая
(2, N'два');    -- вторая
-- результат
insert into @tbl (
	id,
	val
)
values
	(1, N'один'),		-- первая
	(2, N'два');		-- вторая
```

В списке `set` оператора `update` действует то же правило, в том числе для «запятой в начале
строки». Раньше запятая печаталась **после** `--` комментария — она оказывалась
закомментированной, два присваивания сливались без разделителя, и форматтер (правильно)
откатывал форматирование всего скрипта.

```sql
-- вход
update ol
   SET ol.qty = ol.qty + 1 -- инкремент
     , ol.note = N'x'
from dbo.OrderLine as ol
-- результат
update ol
set
	ol.qty = ol.qty + 1,		-- инкремент
	ol.note = N'x'
from dbo.OrderLine as ol
```

```sql
-- вход
insert into #process(object_type, object_id, object_title)
-- результат
insert into #process (
	object_type,
	object_id,
	object_title
)
```

### `2.7` — UPDATE … SET (по строкам) … FROM … WHERE

```sql
-- вход
update w set w.a=t.a, w.b=t.b from t1 as w inner join t2 as t on t.id=w.id
-- результат
update w
set
	w.a = t.a,
	w.b = t.b
from t1 as w
	inner join t2 as t
		on t.id = w.id
```

### `delete` — DELETE FROM … / DELETE alias FROM …
Обе формы поддержаны, с FROM/JOIN и WHERE по тем же правилам, что и SELECT.
WHERE в `update`/`delete` рендерится **так же плоско**, как в `select` — внешние
скобки вокруг условий с `or` не добавляются (см. `where-or`).

### `merge` — MERGE … USING … ON … WHEN … THEN …
Каждое ключевое слово начинает свою строку. Условия `on` — как у джойна: первое на строке `on`
(+1 таб), остальные с `and`/`or` на своих строках (+2 таба). Каждая ветка `when …` — на своей
строке, первое дополнительное условие после `and` остаётся на ней (как в `if`); `then` — на
отдельной строке, действие ветки — на +1 таб. `output` и его `into` — каждый на своей строке.
Необязательное `into` после `merge` сохраняется, если было написано. Комментарии остаются на
своих местах. Раньше `merge` не разбирался вовсе, и скрипт с ним не форматировался.

```sql
-- вход
MERGE dbo.OrderLine AS tgt -- приёмник
USING dbo.Src AS src
   ON tgt.order_id = src.order_id -- условие
WHEN MATCHED AND tgt.qty <> src.qty /* если изменилось */ THEN
    UPDATE SET tgt.qty = src.qty -- количество
WHEN NOT MATCHED BY TARGET THEN -- нет в приёмнике
    INSERT (order_id, qty)
    VALUES (src.order_id, src.qty)
WHEN NOT MATCHED BY SOURCE THEN
    DELETE
OUTPUT $action, inserted.id -- что произошло
INTO #log;
-- результат
merge dbo.OrderLine as tgt		-- приёмник
using dbo.Src as src
	on tgt.order_id = src.order_id		-- условие
when matched and tgt.qty <> src.qty /* если изменилось */
then
	update set
		tgt.qty = src.qty		-- количество
when not matched by target
then		-- нет в приёмнике
	insert (
		order_id,
		qty
	)
	values
		(src.order_id, src.qty)
when not matched by source
then
	delete
output $action, inserted.id		-- что произошло
into #log;
```

Псевдоколонки `$action` / `$IDENTITY` / `$ROWGUID` — один токен (раньше `$action`
превращалось в `$ action`).

## K. CREATE TABLE / DROP TABLE

### `2.14` — CREATE TABLE: `(` на строке имени, типы в нижнем регистре
Колонки — каждая на своей строке (+1 таб). Комментарий колонки остаётся при ней, запятая — **до**
комментария; отдельно стоящий комментарий сохраняет свою строку над колонкой, в том числе
«висячий» после последней колонки — он остаётся над закрывающей скобкой. Раньше комментарий
вклеивался в определение следующей колонки, и такой скрипт не форматировался вовсе.
Табличная переменная `declare @t table ( … )` раскладывается по тем же правилам.

Табличные ограничения (`constraint … primary key clustered (id asc)`) — такие же элементы списка:
ключевые слова в нижний регистр, имя ограничения сохраняет регистр. Пробел перед `(` ставится
там, где он был в исходнике: `decimal(18, 4)` без пробела, `default (0)` — с ним.

```sql
-- вход
declare @tbl table
(
id  int,          -- ключ
val nvarchar(100) -- значение
);
-- результат
declare @tbl table (
	id int,		-- ключ
	val nvarchar(100)		-- значение
);
```

`drop table [if exists] name` поддержан: имя таблицы
заканчивается на следующем операторе или на `end`/`else`, поэтому `drop table #t` в блоке
`begin … end` больше не «съедает» закрывающий `end`, а `drop table #t` перед `update`/`exec`/`print`
не склеивается с ним в одно имя.

Внутри определения колонки имя с схемой пишется слитно (`references dbo.Accounts(id)`),
а комментарий остаётся там, где написан:

- если за комментарием в определении ещё идёт код — он остаётся внутри определения
  (`id int /*x*/ not null`), а строчный `--` переписывается в блочный: за ним обязан идти код;
- если за ним стоит только запятая или закрывающая скобка — это хвостовой комментарий колонки,
  он уходит за запятую (`id int,⇥⇥--note`).

Раньше комментарий в середине определения обрывал колонку и между половинками появлялась
лишняя запятая — скрипт менял смысл.

```sql
-- вход
create table t (
	id int --note
	, b int
)
-- результат
create table t (
	id int,		--note
	b int
)
```

`drop` любого другого объекта — `function`, `procedure`, `view`, `index`, `trigger` — печатается
как обычный оператор: ключевые слова в нижний регистр, имя без изменений. `if exists` в такой
форме относится к самому `drop`, а не начинает новый `if`.

```sql
-- вход
IF OBJECT_ID('dbo.GetBgbillingRawJson', 'FS') IS NOT NULL
    DROP FUNCTION dbo.GetBgbillingRawJson
GO
-- результат
if object_id('dbo.GetBgbillingRawJson', 'FS') is not null
drop function dbo.GetBgbillingRawJson

GO
```

Оператор `drop table` занимает одну строку, поэтому комментарий, написанный внутри него,
остаётся на этой же строке — на своём месте (перед `table`, перед `if exists` или перед именем).
Строчный `--` при этом переписывается в блочный: за ним обязан идти код (правило `cmt-safety`).

```sql
-- вход
drop --note
table #flag
-- результат
drop /*note*/ table #flag
```

```sql
-- вход
CREATE TABLE #x(
	process INT,
	process_status_id INT
)
-- результат
create table #x (
	process int,
	process_status_id int
)
```

## L. CTE · IF/ELSE/WHILE · TRY/CATCH · BEGIN/END · UNION

### `cte` — WITH … AS ( … )

```sql
-- вход
WITH cte AS (SELECT s.[Id] FROM [dbo].[Src] s WHERE s.[Val]>0)
SELECT c.[Id] FROM cte c
-- результат
with cte as (
	select
		s.[Id]
	from [dbo].[Src] as s
	where
		s.[Val] > 0
)
select
	c.[Id]
from cte as c
```

Список CTE может стоять не только перед `select`, но и перед `insert`, `update`, `delete` —
заголовок `with … as ( … )` печатается так же, а сам оператор начинается со следующей строки.
Раньше после CTE ожидался строго `select`, поэтому `with … insert into … select …` не
разбирался и такой скрипт не форматировался целиком.

```sql
-- вход
;with corr as (select * from #dr as dr where dr.groupID=4)
insert into #dr (dt, summa)
select corr.dt, sum(corr.summa) as summa
from corr as corr
group by corr.dt
-- результат
;with corr as (
	select
		*
	from #dr as dr
	where
		dr.groupID = 4
)
insert into #dr (
	dt,
	summa
)
select
	corr.dt,
	sum(corr.summa) as summa
from corr as corr
group by
	corr.dt
```

### `if` — IF / ELSE / WHILE: первое условие на строке ключевого слова, тело на следующей строке
- первое условие остаётся на строке `if`, каждое следующее — на своей строке с одним табом
  (`and` / `or` начинают строку);
- тело (оператор, который выполняется при соблюдении условий) идёт **на следующей строке
  без пустой строки и без дополнительного таба** — на том же уровне, что и `if`;
- то же для `else`: ключевое слово на своей строке на уровне `if`, тело — на следующей строке;
  комментарий, написанный на строке `else` (`else -- режим записи`), остаётся на ней;
- если **всё** условие взято в скобки (`while ( … )`), оно раскладывается как скобочная группа:
  `(` остаётся на строке ключевого слова, условие — на таб глубже, `)` — на своей строке;
- незакрытая скобка перед телом (`while (a <= b select 20` — забытая `)`) закрывается по месту:
  это единственное прочтение, при котором скрипт валиден. Если же текст просто **оборван** в
  конце выделения, скобка не дорисовывается и скрипт возвращается как есть (см. `parse-safety`);
- если телом служит блок `begin … end`, он тоже начинается на следующей строке на уровне `if`;
  пустые строки внутри блока даёт правило `2.8`;
- `while` оформляется точно так же, как `if`.

```sql
-- вход
while 1 < 2 and 20>5
begin
select
1
set @r += 1
end
-- результат
while 1 < 2
	and 20 > 5
begin

	select
		1

	set @r += 1

end
```

```sql
-- вход
if @i < 1 and @b >= 1
print('1')
else
print('0')
-- результат
if @i < 1
	and @b >= 1
print('1')
else
print('0')
```

```sql
-- вход
if @i < 1 and @b >= 1
begin
print('1')
end
else
begin
print('0')
end
-- результат
if @i < 1
	and @b >= 1
begin

	print('1')

end
else
begin

	print('0')

end
```

`else` и `end` больше не «поглощаются» телом ветки: `print('1') else print('0')` разбирается
как две ветки одного `if`, а `begin print('1') end` — как блок с закрывающим `end`
(`end`, закрывающий `case` внутри оператора, границей не считается).

### `trycatch` — BEGIN TRY / BEGIN CATCH
`begin try … end try` и `begin catch … end catch` — самостоятельные блоки (раньше `try`/`catch`
принимались за отдельные операторы внутри обычного `begin … end`, и разметка ломалась). Внутри —
правило `2.8` (пустая строка после `begin`, тело +1 таб, пустая строка перед `end`), а сам блок
всегда отделяется пустой строкой от того, что стоит до и после него.

```sql
-- вход
begin transaction
begin try
delete from p
where id = 980
end try
begin catch
if @@TRANCOUNT > 0
rollback transaction
end catch
if @@TRANCOUNT > 0
commit transaction
-- результат
begin transaction

begin try

	delete from p
	where
		id = 980

end try

begin catch

	if @@TRANCOUNT > 0
	rollback transaction

end catch

if @@TRANCOUNT > 0
commit transaction
```

`begin try`, закрытый просто `end` (без `try`), не форматируется — исходник возвращается без
изменений (см. `parse-safety`).

### `2.8` — BEGIN / END: пустая строка после begin и перед end, тело +1 таб

```sql
-- вход
BEGIN
DECLARE @a INT=1, @b INT=2
SELECT @a, @b
END
-- результат
begin

	declare @a int = 1,
		@b int = 2

	select
		@a,
		@b

end
```

### `2.11` — UNION / UNION ALL / EXCEPT / INTERSECT: пустая строка до и после

```sql
-- вход
select a from t1 union all select a from t2
-- результат
select
	a
from t1

union all

select
	a
from t2
```

## M. Фрагменты (частичные выделения)

### `fragment` — Форматирование неполных конструкций
Если выделение — не целый оператор, форматтер распознаёт: голый `WHERE` (или список условий без `where`), список колонок, цепочку `JOIN`, `GROUP BY`, `ORDER BY`. Раскладка совпадает с тем, как та же конструкция выглядит внутри полного SELECT — фрагмент можно вставить обратно без переиндентации.

Список колонок распознаётся только при **двух и более** колонках через запятую — иначе
любой нераспознанный оператор из двух слов (`use mydb`, `waitfor delay '…'`) превращался
бы в фиктивную колонку `x as y`. Одиночные нераспознанные операторы выводятся как есть.

```sql
-- вход (голый WHERE)
WHERE a.id = 1 AND b.x > 0
-- результат
where
	a.id = 1
	and b.x > 0
```

## N. Как писать тесты

**Формат кейса.** Добавьте запись в список `All()` в `TsqlFormatter.Tests/TestCases.cs`.
Табы в `Expected` — реальные символы `\t`. Сравнение игнорирует хвостовые пробелы строк
и переводы строк по краям, но учитывает отступы.

```csharp
new TestCase {
    Rule = "2.14", Name = "краткое описание",
    Input    = "CREATE TABLE #x(process INT)",
    Expected = "create table #x (\n\tprocess int\n)",
},
```

**Запуск.**

- `run-tests.bat` — все тесты
- `run-tests.bat --rule 2.6` — только правило `2.6` (значение поля `Rule`)
- `run-tests.bat -v` — печатать вывод каждого кейса

Каждый кейс дополнительно проверяется на **идемпотентность** — форматирование результата
ещё раз должно давать тот же текст. При падении печатается построчный diff (зелёным —
ожидаемое, красным — фактическое; табы показаны как `→`).

**Поле `Rule`** — это метка id из заголовков выше (`2.1`, `window`, `convert`, `stmtbound`…).
Она группирует вывод и позволяет фильтровать запуск. Можно вводить свои метки для новых правил.
